# AiPanel: как выпускать фичу

Правила пересборки (что и когда собирать) — в `AGENTS.md`. Здесь — порядок выпуска: проверить, пересобрать, поднять версию, закоммитить только своё, отправить.

## 1. Проверить

```sh
cargo test --workspace
node tests/ui/feed.mjs                        # если менялась crates/server/static
node tests/ui/rename.mjs                      # если менялось переименование сессий
node tests/e2e/real.mjs                       # если менялись агент, сервер или протокол
node tests/hl.mjs                             # если менялся hl.js (подсветка)
```

`tests/e2e/real.mjs` сам собирает агент и сервер, поднимает их на свободном порту и проверяет путь целиком в настоящем браузере. Нужны cargo и Chrome; без них тест пропускается.

Плюс проверить саму фичу так, как её будет использовать человек: в браузере — с компьютера и с телефона (узкий экран), в агенте — на живой сессии.

## 2. Пересобрать изменённое

**Агент** (`crates/agent`, `crates/proto`):

```sh
cargo build --release -p aipanel-agent
```

Затем заменить **обе** установленные копии — локальную и боевую, каждую по процедуре из `AGENTS.md`: `stop` → замена exe → `status` с проверкой соединения. Флаг `--config`/`--home` указывать на каталог этого экземпляра. Пути к копиям, их адреса и имена задач планировщика — в `.local/infra.md`.

Запущенный exe держат обёртки `run-window` от открытых окон агента, поэтому переименовать его может не получиться. Тогда копировать поверх (`Copy-Item -Force`) и сверять `Get-FileHash` установленного файла с собранным: если хеши разные, exe всё-таки занят.

**Сервер** (`crates/server`, в том числе `static`):

```sh
docker compose up -d --build
```

Дождаться `/healthz` и сверить, что панель отдаёт файлы из репозитория: SHA-256 для каждой части `app.*.js`, `style.css`, `/`, `md.js`, `hl.js`, `suggest.js`. Адрес локальной панели — в `.local/infra.md`. `index.html` отдаётся по корню, а не по `/index.html` — иначе получите 404 и пустой файл. Если хеш не совпал, образ собран не из рабочей копии.

Хеш рабочей копии можно сравнивать с боевым и с `git show HEAD:<путь>` напрямую: `.gitattributes` требует LF во всём дереве, поэтому байты файла, коммита и собранного образа совпадают. Если хеши разошлись на размер разницы в число строк — значит, где-то файл снова сохранили с CRLF; лечится пересохранением файла (см. «Переводы строк» в `AGENTS.md`), а не пересчётом хешей.

## 3. Поднять версию

Каждый выпуск (пуш в `master`) идёт с новой версией. Она одна на весь воркспейс — `version` в `[workspace.package]` корневого `Cargo.toml` — и показывается в панели после имени пользователя как `major.minor`, а через слеш — версия агентов в сети: `stas · 9.15 / 9.15`. Патч-разряд всегда `0`.

- Небольшой фикс или мелкая доработка — минор: `1.0.0` → `1.1.0`.
- Большая фича или несовместимое изменение (протокол агента, формат конфига) — мажор, минор сбрасывается: `1.4.0` → `2.0.0`.

`Cargo.lock` после правки версии обновится сам при сборке — его коммитить вместе с `Cargo.toml`. Версию поднимать в том же коммите, что и фичу, или отдельным коммитом `Правила: версия X.Y` прямо перед пушем. Если параллельная сессия успела выпустить свою версию, номера сталкиваются — порядок действий в разделе 5 («Перед пушем»).

## 4. Закоммитить только файлы этой фичи

Скриптов выпуска нет намеренно: коммитить всё дерево нельзя, в рабочей копии может лежать незаконченная работа другой задачи.

1. Посмотреть `git status --short` и отобрать пути, которые относятся к задаче.
2. Индексировать их явно: `git add <путь> [<путь> ...]` — не `git add -A`, не `git add .`.
3. Проверить `git diff --cached`: чужих правок быть не должно. Если в тех же файлах есть чужие незакоммиченные изменения (так бывает, когда параллельно работает другая сессия), индексировать только свои участки: собрать версию файла как `HEAD` + свои правки, `git hash-object -w` и `git update-index --cacheinfo`.
4. Сообщение — одна строка в стиле проекта: `Панель: …`, `Агент: …`, `Сервер: …` или `Правила: …`. Тело — что и почему, если из заголовка это не очевидно.

## 5. Отправить и проверить боевую панель

### Перед пушем: сверить версию с сервером

В рабочей копии могут идти несколько сессий, и каждая поднимает версию по своему `Cargo.toml`. Поэтому прямо перед пушем:

```sh
git fetch origin
git log --oneline master..origin/master          # что выпущено без нас
git show origin/master:Cargo.toml | grep '^version'
grep '^version' Cargo.toml
```

Конфликт версий — любой из случаев:

- на `origin/master` версия такая же или выше нашей;
- `origin/master` ушёл вперёд (`master..origin/master` не пусто), или пуш отклонён с `incorrect old value` / `non-fast-forward`.

Что делать:

1. Влить чужие коммиты (`git rebase origin/master` или `git merge origin/master`), не затирая их правок.
2. Поднять версию **от серверной**, а не от своей: на сервере `9.6`, у нас `9.5` — выпускаем `9.7` (или `10.0`, если нужен мажор). Своя прежняя версия при этом пропадает, это нормально: версия показывает порядок выпусков, а не задачу. Коммит — вместе с фичей (`--amend`, пока не отправлено) или отдельный `Правила: версия X.Y`; `Cargo.lock` с ним.
3. Снова `git fetch origin`: за время правки сервер мог уйти ещё дальше. Пушить только когда `origin/master` — предок нашего `master`.
4. Привести установленное к выпускаемой версии: пересобрать агента и заменить обе копии, пересобрать локальную панель (раздел 2). Версии агентов, локальной и боевой панели должны совпадать с `Cargo.toml` в `master`.

Версию, которую поднял чужой коммит, не откатывать и не «исправлять» — её уже могли развернуть.

### Пуш

```sh
git push origin master
```

Автодеплой идёт только с `master`: хостинг собирает образ и перезапускает контейнер по пушу. Пуш в другую ветку ничего не разворачивает. Сборка небыстрая — в первый раз панель отдавала новые файлы больше чем через 10 минут после пуша, так что не спешить с выводом «деплой упал». Адрес боевой панели и порядок проверки — в `.local/infra.md`.

Порядок проверки:

1. Опрашивать боевую панель (адрес — в `.local/infra.md`) раз в 30–60 секунд, до 20 минут: сравнить SHA-256 изменённых файлов с рабочей копией. До совпадения фича не выпущена.
2. Если через 20 минут хеш всё ещё старый — смотреть статус сборки в панели хостинга: скорее всего, упала сборка, а не «ещё собирается».
3. После совпадения хешей проверить версию: `GET /api/me` (нужна сессия, без неё 401) должен вернуть `{"user":"…","version":"X.Y"}` из `Cargo.toml`. Статика встроена в бинарник, поэтому новый `app.js` уже доказывает, что версия в образе новая, но проверить сам ответ дешевле, чем искать расхождение потом.
4. `GET /healthz` → 200 `ok`.
